## Capabilities

Successful Finance tools persist a compact business card in `tool/result.meta` through `withFinanceCard`. It reuses each tool's existing Host presenter, keeps the full result available to the model, and gives the Web Client a replayable summary without displaying raw arguments or internal JSON. Failed calls do not claim a success card.

Write-off not-sent outcomes retain the bounded last `preflightStage` through durable recovery and tool results. It identifies a local check, not a vendor root cause or retry permission; `final-confirmation` denotes the final Host callback after consent. Older outcomes without a stage remain readable and unmodified. No raw exception or credential is returned. See the [diagnostic decision](../../../.agents/notes/implemented/bug-fix/2026-09-14-write-off-preflight-diagnostics.md).

Finance-only `finance_open_item_accounts` reads account attributes on an explicit existing-open-item page, not a complete directory. `finance_prepare_open_item` prepares/revises with the same-direction `accountReferenceQuery` or inspects the original local ID. Only observed enabled base-currency accounts are accepted; missing IDs/flags remain unknown and conflicting attributes reject. The preview retains its source query/record and does not scan other periods. Accounts absent from that page, including first-ever records, remain unresolved.

Open-item preparation validates direction, exact-cent positive amounts, dates and same-ledger reference IDs. Fresh category/item reads produce `auxiliaryItemNames` as `categoryName:itemName`; ambiguous names, disabled items and unsupported delimiters reject, while absent item status stays unknown. `finance_create_open_item` accepts only the local ID/version and requires mandatory one-time approval of the complete preview. The Host rechecks configuration, source account attributes and selected categories/items after approval and before dispatch. It never creates missing references, receives/pays money, settles balances or generates vouchers.

Owner-scoped atomic records recheck the version under lock and persist uncertainty plus the exact request before one POST. Restart and concurrent calls do not permit resending that operation; this is not cross-operation duplicate detection. The sender reconstructs the fixed request, verifies unique ledger identity, does not retry writes and preserves accepted IDs after cancellation. Lost/invalid/oversized/HTTP-failed or secret-bearing responses remain unknown. The Host saves the transport outcome before independent accepted-ID readback, bounded to the submitted month/direction. Content, account/category/counterparty associations and initial outstanding balance are compared separately; missing, repeated or failed pages remain unavailable. Assembled keyless application scenarios exercise confirmation, revision, denial and durable result recovery; they do not establish full live F3A acceptance.

Internal scalar subject preparation checks code/parent/category consistency, UTF-8 capacity, enabled same-ledger parents and returned duplicates. Other-parent name matches remain visible; current or unknown leaves require historical-impact qualification before promotion. The qualified scalar submission mapping uses debit=false and credit=true, despite the inverse public description. Readback compares original values and configuration independently; it never rewrites the proposal to match an unexpected result. A root uses a four-digit code and null parent in the proposal, omits parent fields in the public request, and requires an explicit empty parent code in readback; an omitted response field remains unavailable. Explicit accounting selections resolve same-ledger auxiliary categories and currencies already observed on current subjects. Both code arrays are required when accounting is provided; omission preserves ordinary behavior. The approved selection retains IDs/names, and readback compares exact configuration without adding a base currency. Unknown or conflicting references reject; this does not register currencies, set exchange rates or promote existing leaves. See the [accounting-options decision](../../../.agents/notes/implemented/feature/2026-09-14-subject-accounting-options.md).

Internal auxiliary-item preparation validates explicit category, code, name, maker and requested status against same-ledger returned references. It rejects filtered reference subsets, category ambiguity and returned duplicate names/codes, and never creates a category implicitly. The six-field request requires a real vendor member as maker. Independent public readback verifies returned category/code/name but omits status; matched identity does not mean enabled/disabled verification. See the [F3A proposal](../../../.agents/notes/proposed/feature/2026-09-09-finance-business-creation.md).

Finance-only `finance_prepare_master_data` prepares or revises with top-level action/kind/input and inspects with action/id; `finance_create_master_data` accepts only a saved ID/version and requires mandatory one-time confirmation. The Host checks references and configuration again after approval and before dispatch. Ordinary subject creation supports a root whose type appears under the same total category in current-ledger references, or an enabled existing branch with matching type and no quantity, auxiliary or currency accounting. Quantity accounting is not supported for either path. Subject types retain the vendor's names, not invented enums; a mismatch rejects without rewriting the proposal. Auxiliary preparation rechecks category identity across both category and item queries. Makers use user-confirmed Finance member names, never reimbursement user/staff lookup as substitute evidence. The tools do not create missing categories or alter existing records.

Master-data records keep owner-scoped editable versions and exact reserved requests. A shared local ledger/kind/category/code claim prevents another preview or session bypassing an accepted or unknown submission; only a durable explicit rejection or proven non-send allows a separately confirmed new attempt. Crashes between target claiming and record saving remain conservatively blocked. This is not cross-device idempotency. The adapter never retries writes and retains acceptance without inventing an ID. Independent original-code readback retains missing fields and changed category identities as unavailable or mismatched. Matching content does not convert an unknown transport outcome to success or permit resending. Auxiliary status remains unverified; complete requires accepted transport and all supported comparisons. Assembled application snapshots exercise the real confirmation/result UI with simulated vendor responses, not live acceptance of all F3A capabilities.

Finance-only `finance_prepare_journal` prepares, revises or inspects a session-owned journal record. The Host checks positive exact-cent amounts, dates, enabled cash-account IDs and same-ledger category selection. Request mapping uses the cash-account ID in subjectId, null for the inactive income/expense side and an explicitly displayed predecessor. Category direction and returned-name ambiguity are checked before mapping to categoryName. The insertion point follows the last returned row of a bounded date/account page, or zero when that page is empty; this is not a claim of exhaustive history. See the [F3A proposal](../../../.agents/notes/proposed/feature/2026-09-09-finance-business-creation.md).

`finance_create_journal` accepts only a local ID and version and requires one-time mandatory confirmation of the complete preview. The Host rechecks configuration, references and insertion position after confirmation and before sending. Returned cash-account currency ID, account type and raw direction participate in this comparison; changed or removed attributes invalidate approval. Missing attributes remain absent rather than inferred. Owner-scoped atomic records recheck the version under lock and persist uncertainty plus the complete request before dispatch. Restart, cancellation and unknown outcomes do not permit automatic resubmission. The adapter never uses read retries for writes. Returned string IDs mean accepted, not verified. The consumer's configurable maxBytes bounds complete previews and durable records.

Journal readback uses the accepted ID and bounded date/account pagination. It compares business fields, category ID rather than the vendor's direction-prefixed display name, predecessor, unreviewed status and returned empty associations. Missing fields or records remain unavailable; wrong fields remain mismatched. A missing inactive amount is compared with the reserved null side, not converted into a reported zero. Completion describes this record's technical comparison, not complete journal coverage or actual money movement. Creation does not call voucher generation, review, write-off or payment APIs; inspect only reads the original operation and its accepted ID.

F2 preparation validation rejects malformed dates/amounts, duplicate auxiliary categories and unbalanced cent totals. A read-only resolver verifies exact reference codes, enabled leaf subjects, required auxiliary/currency configuration and ledger identity. Unknown auxiliary status stays unknown. Foreign amounts multiplied by user-confirmed rates must match each base amount after decimal half-up rounding to cents; validation never changes input. These helpers do not establish writable periods or appropriate rate selection, or authorize writes; see the [creation decision](../../../.agents/notes/implemented/feature/2026-09-09-finance-voucher-creation.md).

Internal voucher records use versioned atomic files scoped by owner and reject stale proposal/configuration versions. Reservation saves the exact payload, destination and appId/flowId with outcome-unknown before returning. Reload reconstructs the payload and rejects mismatches; transport observations persist separately as accepted, rejected, not-sent or outcome-unknown, never verified completion. Records with a reservation cannot be edited or automatically reserved again after restart.

Voucher numbers are optional while preparing but listed in `missingFields` when absent; submission requires the previewed number. The ordinary-endpoint sender verifies account identity and rechecks Host configuration immediately before its single send, independent of read retries. It preserves stable appId/flowId, rejects unmatched attachment counts and lossy JSON numeric conversion, and never populates audit fields or both entry amount sides. An accepted ID is not verified success; response loss, HTTP failures and ambiguous responses remain outcome-unknown.

Submission readback compares the reserved account, accepted ID, number, date/period, maker and entry multiset, rejecting unexpected audited/settled states. A separate per-entry auxiliary comparison preserves duplicates and leading-zero codes. Live reference comparisons show that detail fields `auxiliaryCategoryTypeId` and `auxiliaryCategoryId` contain category/item codes, not reference-row IDs. Missing auxiliary arrays remain unavailable, not empty. Currency verification compares direct entry currencyCode, originalCurrencyAmount and exchangeRate with accounting and auxiliary values as a multiset; it does not use foreignCurrencySimpleList. `complete` requires matched accounting, auxiliary and currency data and either no requested originals or all requested copies independently matched after source expiry. It is per-voucher technical verification, not invoice authenticity, accounting advice correctness, audit/posting or F2 project acceptance. Read failure does not permit resubmission.

Original-copy verification reads detail `attachmentList.downloadUrl` only from exact Config `youchengAttachmentHosts` (default `yiqicai.oss-cn-zhangjiakou.aliyuncs.com`). HTTPS, no credentials/fragment/nondefault port, no redirects and no reuse of a source object URL are required. Downloads have a whole-check `attachmentRequestTimeoutMs` deadline and aggregate `youchengAttachmentVerificationMaxBytes` cap (default20000000). Actual size/SHA256 multisets determine association; vendor filenames and declared sizes are untrusted metadata and never displayed by this verifier. Matched copies are retention-pending until verification starts after every selected source link expires, then verified. Missing, disallowed or unreadable copies remain unavailable; wrong counts/content are mismatches. None permits another creation. Safe upload receipts retain their own unverified association label; `readback.originals` carries independent current copy evidence.

`inspect` also reads reserved records after restart. It checks the saved configuration digest before querying an accepted ID; unknown outcomes without an ID remain unknown and require manual verification. It returns no private submission payload or attachment URLs. Failed readback preserves the accepted ID.

`finance_create_voucher` accepts only a prepared ID/version. The Host presents the complete preview for mandatory one-time approval, revalidates unchanged content/references/configuration, reserves durably and sends once. Credential/configuration changes during authentication prevent dispatch. Post-send cancellation or failed readback cannot erase a persisted outcome. Host configuration `youchengVoucherAppId` defaults to `xiaojing-accounting`; flowId is the record UUID. Both tools are Finance-only. Foreign-currency creation requires configured subject support and validated conversion. Writable periods are not independently qualified and remain subject to vendor write validation, disclosed in confirmation. Simulated vendor responses do not qualify live write acceptance.

Selected PDF/PNG/JPEG originals use financial-voucher approval, never reimbursement consent. The approved storage target and its revision are checked before uploads; imported file ownership, bounded bytes, size/hash and format header are rechecked. Uploads carry the extension-specific media type. Vendor-facing download URLs use a short-lived OSS compatibility signature and end with an explicit extension-bearing inline filename; they omit a response-media query value whose slash can corrupt a vendor-derived filename. Other OSS transfers retain V4 signing. Each private upload receipt is saved before creating the voucher, and every selected original must match a persisted URL. Any upload, receipt or configuration failure prevents creation; already-uploaded objects remain, with saved receipts visible without signed URLs. Revisions retain earlier upload receipts but submit only currently selected originals. Reservation also reserves byte capacity for the longest accepted identifier. Expired URLs prevent dispatch. Upload and URL delivery do not establish vendor transfer or retention after expiry.

`finance_prepare_voucher` exposes `prepareVoucher` in the Finance preset: prepare, revise and inspect local previews, never submit. Revision requires the last returned version. Sources must belong to the session's import log and source directory; preparation, revision and inspection reread bounded bytes and reject changed sizes/hashes. This verifies imported bytes, not invoice authenticity or successful transfer. Client-version and credential changes invalidate the configuration digest. Tool configuration bounds entries (`maxEntries`, default100) and full records/results (`maxBytes`, default131072). Results explicitly retain pending checks and are not confirmation or proof of creation.

Xiaojing Finance Host capability for local taxpayer-entity records and immutable per-session client context. The Cordis plugin owns storage, revision-safe mutations, pre-turn selection, durable session binding, the browser Remote, and model-visible Finance context. It does not modify the Agent Loop and is loaded only by the Xiaojing product composition.

## Client records

Bound Finance sessions receive fixed read-evidence instructions on every model request, independently of optional skill loading. Cross-source comparisons require verified account mapping, currency, period basis, population and accounting status; unknown fields remain scoped to their source and subject. These instructions constrain interpretation, not vendor data completeness or model correctness.

One record represents one independent taxpayer entity. Mutations require the legal name, short name, taxpayer type, registered region, and accounting standard; historical records may omit the short name until their next edit. Optional business fields include a unified social credit code, industry, and finance-policy notes. A record may also select one finance system. Youcheng stores its test/production environment, AppKey, ledger ID, and selected ledger name in the client catalog; SDOO, Yonyou, and Kingdee are selection placeholders until their connectors define configuration fields. Account mappings are retained for existing domain consumers but are not manually maintained by the client-details form.

A Youcheng AppSecret is stored as a per-client record through `ctx.credentials`, never in `clients-v1.json`, a Workspace profile snapshot, or a session event. Full-detail reads expose only whether that secret is configured and writable. Enabling Youcheng requires a stored or newly supplied AppSecret; omitting the value on a later update preserves the stored credential. The catalog lock encloses credential preparation, and a failed catalog write restores the previous credential before releasing that lock.

The catalog is stored at `$DSH_HOME/finance/clients-v1.json` with schema version `1`. Each mutation supplies the whole-file `expectedRevision`; a stale editor is rejected instead of overwriting another window. Writes use a file lock and atomic replacement. A corrupt document fails plugin startup and remains unchanged. Records can be archived but not physically deleted; archived records remain available to historical sessions and cannot start new sessions.

## Youcheng connection verification

One customer selects one ledger ID, stored in `financeSystem.accountCode` and sent as `setOfBooksId`. The loopback-only `financeClients.checkConnection` reads saved credentials, authenticates, and matches exactly one ID in the returned account list; a matching name or the first account is insufficient. The adapter follows the [V2 Finance API reference](https://yiqbopenapi.superboss.cc/#/share/awXPk8nW/JzAPN6Xp), using `/auth/getAccessToken.rjson` and `/finance/auxiliary/queryAccountList.rjson`. Verification returns only the selected account and never writes accounting data or returns tokens or vendor error bodies.

The loopback-only `financeClients.listYouchengAccounts` accepts the open editor's revision, environment, AppKey, and optional unsaved AppSecret. An omitted secret reuses only that customer's stored credential. Discovery sends no ledger ID and returns only authorized ledger IDs and names; it does not infer which ledgers belong to the customer. It rejects stale revisions and archived customers, distinguishes an empty list from a failed request, and changes neither the saved record, credentials, connection badge, nor the saved-connection token cache. Discovery uses the same request deadline and is awaited during Host teardown.

Host Config fields `youchengTestApiUrl` and `youchengProductionApiUrl` both default to `https://cwdata.yiqiyun.com`. Test and production are internal labels, not assertions about vendor infrastructure; both may resolve to the same HTTPS origin. The editor displays the resolved address read-only. `youchengRequestTimeoutMs` defaults to 20000 for the complete check. Redirects are rejected. Tokens stay in Host memory and are reused for up to 115 minutes for unchanged credentials and origin.

Verification status lives in Host memory and is invalidated by client edits, credential replacement, or Host restart. In-flight checks cannot publish success for a superseded configuration. Green indicates that the latest authentication and exact-ledger lookup passed, not general business-operation permission or continuous availability; red carries a safe failure category, while unverified state is gray. Saving client details and checking the connection are separate operations: a failed check does not undo a successful save.

Verification distinguishes transport failure from the whole-check timeout, including response-body reads. HTTP 401 reports authentication failure; HTTP 403 reports access denial without assuming whether permissions or an access policy caused it. An explicit vendor IP-allowlist rejection takes precedence. Only safe categories reach the Client; raw bodies remain private.

## Finance reference queries

Direction notices apply only to the queried kind. Subject direction is independently qualified as 0 debit/1 credit. Missing direction cannot be inferred from names or accounting conventions. These model instructions reduce ambiguity but do not guarantee that every generated explanation complies.

Subject rows retain the bounded vendor subjectType name, distinct from the code's total category. Missing or null values are omitted; an empty string remains empty, and neither permits inference. Tool descriptions and returned notices use the same qualified direction meanings. This adds no category filter, implicit parent attributes or write authority.

The Finance-only `finance_references` tool queries subjects, auxiliary categories/items, cash accounts, and receipt/payment categories from the session's saved ledger. A subject query may name a root code and request its complete returned subtree; the Host first resolves the unique root, fetches subject rows without model-side filtering, and follows parent identities until every reachable descendant has been collected. The Host rechecks exact ledger identity and unique name, validates an item's category before querying, and discards results after configuration or credential changes. No input overrides the ledger, origin, or secret, and no missing record is created. Structured rows are serialized as JSON in the logged result and generic read card; no raw vendor payload is forwarded.

`youchengReferenceMaxRows` defaults to 1000 and is sent as `pageSize`; `youchengReferenceMaxBytes` defaults to 262144 for each response and the complete emitted result. The whole operation uses `youchengRequestTimeoutMs`. These APIs expose no documented page/cursor or total, and some ignore `pageSize`, so `coverage` is always `unverified`; exceeding either cap fails instead of silently truncating. Exact name/code filters apply only to the returned set. All same-name candidates remain visible; a unique returned match is not a globally unique selection.

Rows retain available subject parent/child relationships, auxiliary and currency codes, and endpoint-specific enabled/disabled states; absent state is `unknown`. Direction values remain raw: subject and cash-account directions are independently qualified as 0 debit/1 credit, while cash-category direction is 0 receipt/1 payment. Missing upstream parent rows and direction values are not fabricated.

## Temporary voucher query

The Host records a safe diagnostic category and stage (authentication, ledger verification, request, or response validation). Transport exceptions become `network`; recognized reset, socket, DNS and connection-timeout cause codes are appended from a fixed allowlist. Unknown codes, raw exception messages and request URLs are never recorded as model results. Rejected projections become `invalid-response` internally. Host Config `youchengRetryTransientReads` defaults to `true`: authentication and read requests retry once on `ECONNRESET`, `UND_ERR_SOCKET`, `EAI_AGAIN` or `UND_ERR_CONNECT_TIMEOUT`, using the identical request and original deadline. Cancellation, permanent DNS failure, HTTP/vendor failures and invalid responses are not retried. The model receives one plain-language actionable failure instead of these diagnostics. A failed read is not an empty result and does not identify a vendor or configuration defect by itself.

`finance_voucher_detail` reads one voucher through `/finance/certificate/info.rjson`. The Host shares session/workspace ownership and stale-credential checks with the list query; the adapter matches both returned `accountId` and `certificateId` before publishing. Details expose decimal-string entry amounts, voucher date, accounting period, maker, and audit/settlement booleans. Attachments, auxiliary accounting, and foreign-currency details are excluded with an explicit notice, not represented as absent. The tool uses a known list ID or user-supplied ID; ambiguous references require candidate selection, not a guessed ID.

Natural-language intent belongs to the agent, not the vendor summary filter. For paraphrases or business meanings, the tool instructs the agent to omit `summary` and inspect bounded period pages using all entries, subjects, directions, and amounts. Keyword misses do not prove absence. A non-first empty page carries a warning that the vendor can return `count: 0` for an out-of-range page; the agent must recheck page one before reporting a zero total. These instructions do not establish live-model semantic acceptance.

The Finance preset exposes the read-only `finance_vouchers` tool through `./vouchers-tool`, calling the [V2 Finance voucher list](https://yiqbopenapi.superboss.cc/#/share/awXPk8nW/aXYwLJ2r), not the reimbursement export endpoint. The Host derives the customer from the session binding, verifies its workspace, and resolves the saved ID to one authorized, uniquely named ledger because the API accepts `accountName`. Consultation, Standard sessions, missing connections, ambiguous names, and concurrent record edits are rejected. Queries use current saved connection settings without changing historical customer facts. Credentials and vendor error bodies never enter results.

`month` accepts an accounting period `YYYY-MM` or `current` (Beijing month); omission queries all periods without promising latest-first order. Voucher dates do not independently verify accounting periods. Each call returns one page, the vendor-reported filtered total, continuation status, entry rows with decimal debit/credit strings, and a scope notice. `page` defaults to 1; configured `pageSize` defaults to 20 and accepts 1–100. Unexpected query fields, inconsistent page lengths or duplicate IDs fail; an empty page beyond the total is not an empty ledger. Numeric amounts beyond safe cent precision require a vendor decimal string. `youchengVoucherMaxResultBytes` defaults to 65536 for each response and the complete result. Configuration or credential changes discard in-flight results. Cancellation and Host teardown abort requests. Logged tool calls render query/result cards; a green connection badge is not query permission. `finance_vouchers` returns list pages, while `finance_voucher_detail` performs the separate detail lookup.

`monthEnd` adds an inclusive period range and requires a start not later than the end. `summary` is passed unchanged to the vendor's `abstractName` filter; empty/whitespace-only values are rejected. Results retain both conditions and every returned voucher entry, including lines whose summaries differ. Subsequent pages must retain the same conditions and page size. Exact versus fuzzy summary matching and nonempty period filtering remain unverified; the tool does not invent delimiters for undocumented multi-value filters.

## Retained private attachments and reimbursement backend

The loopback attachment settings are computer-wide, independent of client records. `ctx.credentials` stores the OSS configuration and write-only RAM key pair together with a revision; reads expose configuration and credential status only. Deployment defaults select bucket `rhy-attachment`, region `oss-cn-hangzhou`, HTTPS CNAME `https://attachments.sudo.vip`, and prefix `xiaojing/`. No key is bundled. A connection test uploads synthetic bytes, downloads them through a signed URL, compares their contents, and attempts to delete only that test object. Saving alone is not a successful connectivity test.

The retained Host attachment operation accepts an unchanged PDF, PNG, or JPEG imported into the current client session. The Host verifies import ownership, canonical source containment, byte count, digest, and file signature before upload. Cloud object keys use client/session identity and content hashes, not taxpayer names. Originals and uploaded invoice objects are preserved. Upload requests store `application/pdf`, `image/png`, or `image/jpeg` on the object; voucher-delivery links end with an extension-bearing generic filename without exposing the source filename or adding a slash-bearing media-type query value. Transfers reject redirects and use `attachmentRequestTimeoutMs` (30000), `attachmentMaxFileBytes` (20000000), and `attachmentUrlExpiresSeconds` (3600); signed URLs remain outside model-visible results. Use a RAM policy limited to this bucket and prefix with object upload, read, and delete permissions. The current Finance preset does not register a standalone attachment-upload tool.

Reimbursement configuration is separate from Finance credentials, even when AppKeys match. A per-client credential record stores its own origin, AppKey, AppSecret, and revision. The default origin is `https://yiqbdata.superboss.cc`; `https://yiqbdatatest.superboss.cc` is also admitted. Reimbursement identity comes from these credentials, not the financial ledger ID. `reimbursementRequestTimeoutMs` defaults to 60000 and `reimbursementMaxResponseBytes` to 16000000. Discovery projects templates, users, departments, and masked payees without vendor tokens or full bank accounts.

The retained reimbursement operation validates live templates and selected identities, requires one-time user confirmation, uploads imported originals, and sets `orderComponentList`'s fixed `attachment.bindingVal` to a JSON-encoded URL array even when template metadata omits that field. It does not create invoice-ledger entries. A separate required `staff` employee field requires an explicit, eligible `employeeId`, not an inferred applicant identity. Only CNY, single-day dates, text/number extra fields, and supported required components are admitted. Missing or unsupported required fields stop creation. `pushOrderStatus` is fixed to `1`; success requires push-result lookup and readback of the resulting order's pending-submission status. The current Finance preset registers neither `finance_reimbursement` nor the reimbursement skill, so this preserved backend is not a Finance chat capability.

Within the retained backend, a fee template that declares `attachment` receives only that fee's selected original URLs in `feeComponentList`, using the same uploads; required fee attachments are supported. This is ordinary attachment transfer, not invoice-ledger association. Existing draft receipts are not rewritten or resubmitted to backfill missing attachments.

Within the retained backend, pending questions or reimbursement confirmations block creation and standalone attachment uploads. A failed/cancelled question or rejected confirmation blocks subsequent writes until a new human text message; that message permits a new attempt but does not replace mandatory bill confirmation. The Host reconstructs this decision from session events, reads question failure from the tool message isError flag, and rechecks it before external writes.

Private revision-bound receipts live under `$DSH_HOME/finance/reimbursement-operations` as schema-version-1 JSON. They record the session owner, deterministic request ID, progress, filenames, and order code, but no signed links or credentials. A per-owner lock serializes requests. Identical requests reuse the receipt; an uncertain write blocks changed requests in that session and requires readback instead of another creation. This is not cross-session invoice deduplication. User-facing results distinguish verified drafts from pending, failed, and unexpected states. Vendor retention of attachment URLs versus copying of originals remains unverified; expiring links alone do not guarantee durable attachment access.

## Dedicated Finance workspaces

Finance owns a user-visible workspace root separate from ordinary Harness workspaces. The desktop product sets it to `Documents/小兢会计工作区/Finance工作区`; the deployment may provide another absolute `workspaceRoot`. The root contains one fixed Workspace displayed as `Consultation` and one `clients/<client-id>` Workspace per catalog record. Stable ids, rather than editable display names, keep customer paths unchanged when a record is renamed.

Finance add actions expose the canonical `workspaceRoot` to the local Client only as the directory picker's initial location. Deployments may declare `ordinaryWorkspaceRoots`; Finance startup rejects a configured ordinary root that overlaps the Finance root, and Finance creation rejects a selected directory that overlaps either a configured ordinary root or an ordinary Workspace already registered with Workspace Registry.

Creating a client provisions `00-客户档案`, `01-财务政策`, `02-原始资料`, `03-会话作业`, `04-成果输出`, and `05-归档` before committing the catalog record, then registers that client root with the Harness Workspace registry. A failed mutation removes the new registration and directory. Startup removes an incomplete registration left by an interrupted create but preserves its directory and files for recovery. Archiving keeps the Workspace and its history while disabling new sessions.

Workspace display titles and Finance-list membership are stored separately at `$DSH_HOME/finance/workspace-presentation-v1.json` with schema version `1`, a revision, process-safe locking, and atomic replacement. Renaming changes the Harness registration title and this presentation record without changing the directory. Removing a consultation or client Workspace hides it from Finance lists but keeps its registration, directory, customer record, and sessions; selecting the same directory through the add action restores it. At least one consultation Workspace must remain listed.

Client sessions use the selected client root as their immutable `cwd`, with one isolated child under `03-会话作业` per session. Each child atomically stores `会话信息.json` with the session id, client id, client-record version, and display name; full conversation history remains authoritative in the Harness session store, while this directory owns only working files and its identity manifest. An accounting period is not fixed on the client directory or session; tax, ledger, and bookkeeping Skills may create period-specific children for the current task. Consultations must use the fixed consultation root. The Host rejects a consultation in a client root and rejects one client's selection from another client's root.

## Controlled file lifecycle

The unified upload entry remains unchanged for users. In a client-bound Finance session, a completed local upload is copied into `02-原始资料`; the upload staging file is preserved, and supported images also remain native visual attachments. In a general Finance consultation, the Host keeps the file in the protected local upload directory and flushes a session-scoped `finance/consultation-file-imported` event containing its canonical path, display name, size, and SHA-256. Non-Finance sessions retain the ordinary upload behavior.

Each client session performs temporary work only in its own `03-会话作业/<session-id>` directory. The Finance preset adds the `finance_files` tool: natural-language requests for a final version, export, delivery, or formal saved result invoke `publish`, which copies an existing session-work file into `04-成果输出`. Draft, preview, trial, and ambiguous requests stay in session work. Only an explicit archive intent invokes `archive`, which copies a file from this client's original materials, current session work, or formal outputs into a Beijing-date child of `05-归档`. An explicit relative `archiveFolder` instead selects that one safe child under `05-归档`; the operation does not create an additional dated copy. Neither action moves or deletes its source.

## Balance queries

The Finance-only `finance_balances` tool reads inclusive accounting periods through the bound client's saved connection. `youchengBalanceMaxRows` (default 1,000) includes summary rows; `youchengBalanceMaxBytes` (default 262,144) bounds each raw response and the complete result. Amounts preserve vendor debit/credit columns and signs. Blank strings become `null`, not zero; blank movements or equal opening/closing amounts do not establish no activity. Valid thousands separators such as `1,000.00` are removed as text without floating-point conversion; malformed grouping is rejected. Subject rows and vendor summaries remain separate; callers must not sum parent/child rows and summaries together. The observed vendor `count` is zero even for nonempty reports, so `coverage` remains `unverified`. A missing subject row does not prove a zero balance. Broader hierarchy coverage still requires qualification; no conventional net closing balance is inferred from ambiguous fields.

Balance answer instructions preserve debit/credit labels throughout tables and conclusions. Missing values use “未提供” for subject and summary rows alike. Equal amounts do not establish transfers, and generated prose must not add unsupported arithmetic. These instructions require live-answer acceptance; they are not deterministic output validation.

An optional `subjectLevel` selects one positive int32 level through equal vendor start/end levels. Returned subject rows must match that selection; vendor summaries remain separate. The result and workbook retain the selected scope. Omission uses vendor defaults, not a promise to retrieve every child.

Adding `subjectLevelEnd` selects an inclusive level range starting at `subjectLevel`. The adapter reads the initial level, then follows `hasChild` using each parent's `subjectInfoId` as `parentSubjectId` through the requested end level. Requests disable pagination, explicitly select base currency and include disabled subjects. Only initial summaries are retained. Duplicate subjects, wrong parents, missing advertised children, cancellation or combined row/byte limits reject the operation. The result and workbook retain the range; traversal does not independently prove root completeness or permit summing parent and child balances.

Range queries require unique positive subject IDs and nonnegative parent IDs. Returned parents must be exactly one level above their children and advertise children; every noninitial-level row needs its parent. An advertised child must be present below the requested end level. Summary IDs are discarded. These structural checks do not prove that the vendor omitted no unrelated root or sibling.

The Finance analysis skill distinguishes quoted source values from requested calculations. Query answers retain tool field meanings instead of reconstructing balances; requested calculations require verifiable results. Progress and final prose use the user's language and respect declined exports. The assembled balance scenario loads the actual skill before querying to exercise both instruction sources together.

Cross-source comparisons require verified account mapping, currency, period basis, population and accounting status.
