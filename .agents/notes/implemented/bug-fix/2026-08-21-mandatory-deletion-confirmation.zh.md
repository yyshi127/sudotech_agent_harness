# Agent Note：删除操作强制二次确认

Status: implemented

[English](2026-08-21-mandatory-deletion-confirmation.md) | 中文

## 问题

`never` 审批策略会在任何应答者运行前拒绝普通审批请求。Full access 使用该策略，因此当 shell 本身没有请求沙箱升权时，模型发出的 `Remove-Item` 等 `pwsh` 命令可能不经询问直接执行。小兢会计浏览器和 Windows 自动化中的删除控件也存在相同缺口。删除必须独立于普通会话策略获得一次新的用户决定；缺少决定、拒绝、取消或过期时都不能执行。

## 决策

`ApprovalService.requestMandatory()` 复用现有的限定作用域 `approval/request` 应答者链和审计事件对，但不应用普通 `never` 的分发前拒绝。它仍要求位于未结束的轮次内，仍在失败时拒绝，且只有 `allowed-once` 才是授权。`request()` 及其确定性的普通策略行为保持不变。

小兢会计产品插件检测显式删除工具名和 shell 删除命令。其 pre-execute 监听器请求强制确认，并只在授权后标记当前工具执行 token。随后，单调 `tools.guard()` 会拒绝所有缺少该标记的匹配调用，因此其他 pre-execute 监听器无法通过提前结束 waterfall 绕过确认。该标记只消费一次，并在最终结果路径清理。浏览器和 Windows 提供方对删除、移除、卸载目标及明确的 Delete 键操作使用强制请求；其他高影响操作继续使用普通审批。

产品自动化上下文会说明：即使在 Full access 和 `never` 下，删除仍受确认约束，并禁止通过更换或混淆删除命令规避询问。Shell 分类器识别常见 PowerShell、命令行 shell、POSIX、Git、Python、Node.js、.NET、`find` 和 `robocopy` 删除形式。如果新增工具的破坏意图无法从工具名或参数中看出，该工具必须在自身提供方中分类删除操作。

## 考虑过的替代方案

- **把 Full access 视为删除的默认同意。** Full access 适合无人值守的普通工作，但永久数据丢失无法安全撤销，需要更窄的一次性决定。
- **让 `never` 对所有高影响操作提问。** 这会暗中改变现有策略，并让无人值守的普通操作变成交互式。独立的强制入口让例外保持显式。
- **只依赖一个 prepend waterfall 监听器。** 后注册的 prepend 监听器可以不委托就占用 waterfall。单调 guard 是已组合产品运行时内不可被放行结果覆盖的拒绝后备。
- **完整解析每一种 shell 语言。** 多种 shell 与嵌入脚本让完整静态解释不切实际。保守识别覆盖显式的模型生成删除命令，不透明且能够删除的工具则必须在提供方内部强制执行策略。

## 结果

桌面和微信会话现在即使处于 Full access，也会在已识别删除前收到现有确认界面或微信六位确认挑战。拒绝、超时、断线、无可用应答者或未确认的提前放行都会阻止工具执行。该策略不声称能推断任意第三方可执行文件内部隐藏的破坏行为，因此未来每个可删除数据的工具都必须增加显式强制分类和聚焦回归测试。
