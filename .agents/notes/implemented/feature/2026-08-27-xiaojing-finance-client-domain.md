# Agent Note: Xiaojing Finance client domain and immutable session context

Status: implemented

English | [中文](2026-08-27-xiaojing-finance-client-domain.zh.md)

## Problem

Finance mode could research official tax sources but had no durable way to distinguish a general consultation from work for one taxpayer entity. Putting mutable customer fields directly into browser state or rebuilding context from the latest customer record would allow two sessions to mix entities and would change the facts seen by an old conversation after the record was edited. A CRM would add unrelated contacts, sales, contracts, and billing scope without solving model-context integrity.

The implementation also needed to preserve the repository rule that model-visible input is reconstructable from the session log, keep product behavior outside official Harness UI owners, and make future Youcheng and SDOO services reject unbound sessions through one shared guard.

## Decision

`@deepseek-ai/dsh-xiaojing-finance-domain` is the Xiaojing-only Host capability. It stores one record per taxpayer entity in `$DSH_HOME/finance/clients-v1.json`. The document has schema version `1`, a whole-file revision, and record-local versions. Mutations use compare-and-swap revision checks, a process-safe file lock, and atomic replacement. Corrupt data rejects plugin initialization and remains unchanged. Records may be archived but not deleted, so historical session references stay valid. New and updated records require a short display name; historical records without one remain readable until their next edit. A record may select one finance system: Youcheng keeps its environment, AppKey, account-set code, and selected account name as non-secret client data, while SDOO, Yonyou, and Kingdee remain explicit placeholders. The Youcheng AppSecret is a per-client `ctx.credentials` record; reads return only its configured and writable state. Credential preparation runs under the catalog file lock and is rolled back if catalog replacement fails.

A blank Finance session starts in general-consultation state. Client selection is staged only in Host memory before the first turn. The first model request resolves the staged record, appends and flushes one `finance/client-bound` event, then contributes its text to the request. That event contains only the immutable business snapshot and record version; finance-system connection settings and credentials remain outside the event and model prompt. A month, quarter, or year belongs to the specific Finance Skill request and is read from the user instruction or requested when absent; it is not fixed on the client or session. General requests log no binding and receive an explicit no-client context that prohibits inferred customer facts. `requireBoundClient()` is the single precondition for future client-specific finance services.

Request preparation can flush the binding before `turn/start`; interruption in that interval leaves a session both blank and durably bound. Re-entering that customer's Workspace is idempotent: the Host verifies the same client and `cwd`, returns the locked safe view, and still rejects general mode or another client. The Client renders the customer name from that safe view, keeps both selectors locked, and leaves the composer available.

The `financeClient` session projection folds the durable event but exposes only client display name and state to browser clients. Full tax identifiers, policy notes, mappings, external-system identifiers, and finance-system connection settings remain Host data. The generated `financeClients` Remote exposes summaries and safe session state generally; full reads, mutations, and staging are loopback-only. A full client read includes credential status but never the AppSecret, while a mutation may carry a write-only replacement.

`@deepseek-ai/dsh-client-ui-xiaojing-finance-clients` exposes Ledger information from each customer Workspace action menu without a customer-management settings section. The independent [attachment and reimbursement configuration](2026-09-04-reimbursement-draft-attachments.md) preserves this record and session design. Its Ledger labels are presentation only; client records, Remote identifiers, and Workspace paths retain their existing meaning. The modal separates basic client fields from finance-system configuration, requires and explains the compact short name, shows Youcheng fields conditionally, retains unsupported systems as named selections, and omits manual account mappings. It fills the product-neutral `conversation.hero.context` slot only for blank Finance sessions and registers a read-only context label in active session headers. The `Consultation / Ledger` selector lists `short name-ledger name-ID value`, falling back to a historical record's legal name, and adds an owner-scoped composer block only while client mode has no selection. `ComposerBlockRegistry.setOwned()` allows Finance to remove only its own block without clearing independent model, upload, Goal, or Plan constraints.

Finance also owns a file and conversation category separate from ordinary user workspaces. Product configuration fixes its root beneath `小兢会计工作区/Finance工作区`, with one Workspace displayed as `Consultation` for unbound sessions and one `clients/<stable-client-id>` Workspace per taxpayer entity. The client root is the immutable `cwd` for all of that client's sessions and owns profile, policy, source, session-isolated work, deliverable, and archive directories; task Skills create period-specific children when needed. The Host validates the actual `cwd` before staging and model use, structurally rejecting cross-client binding. Client creation provisions directories and registers the Workspace before committing the catalog; failures roll back new resources. Startup recovery removes a registration left by an interrupted create while preserving its files for recovery.

The same Host capability owns a controlled, copy-only lifecycle for those directories. A Client extension event lets the existing upload button hand a completed local upload to Finance only when the session is client-bound; the Host copies it into `02-原始资料`, while consultations and other presets keep the ordinary upload route. Every session owns one `03-会话作业/<session-id>` directory with an atomically written `会话信息.json` identity manifest; complete conversation history remains in the Harness session store, and the customer directory contains only work files plus that manifest. The Finance-only `finance_files` tool copies a session-work file into `04-成果输出` when the user's natural-language request identifies a final, exported, delivered, or formally saved result, and copies an explicitly archived managed file into a date child of `05-归档`. Draft or ambiguous work stays in `03`, and neither operation removes its source.

`.xiaojing-finance-files-v1.json` is an append-only, revisioned index in each client root. It records the owning client and session, operation, absolute committed path, size, SHA-256 digest, and source-record relationship. A successful copy appends and flushes a matching `finance/file-imported`, `finance/file-published`, or `finance/file-archived` session event, making every model-visible managed path reconstructable from the log. Path validation resolves regular non-symlink files against the upload root, current session work directory, or selected client directories. Atomic destination creation and index replacement prevent overwrite and partial metadata; a corrupt index stops the operation without replacing the damaged file. These controls govern the unified upload and Finance tool paths, not arbitrary Full Access shell writes.

`$DSH_HOME/finance/workspace-presentation-v1.json` owns editable Workspace titles and Finance-list membership independently of customer records and Workspace registrations. It uses schema version `1`, a revision, process-safe locking, and atomic replacement. Removing a Workspace is a non-destructive list operation: its registration, directory, customer record, and sessions remain intact, hidden Finance registrations stay reserved from ordinary Workspaces, and selecting the same directory restores the item. The domain rejects removing the final listed consultation Workspace.

Generic `ui-workspace` adds only the `WorkspaceCategoryRegistry` extension point and contains no Finance copy or recognition rule. The extension supports product categories, nested sections, product-neutral semantic section icons, reserved and visible membership, one provider-owned non-destructive detail action, rename and remove operations, and the active preset's Workspace-picker scope. It renders nested sections as contiguous groups in provider order even when the global Workspace registry interleaves their members, while preserving registry order within each section. The Finance Client plugin supplies `Office Companion / Finance Assistant` labels and membership: `Ledgers` uses the ledger icon and precedes `Consultation`, which uses the discussion icon; both icons retain the business accent independently of the active section. Customer row menus order `Ledger information`, `Rename`, and `Remove workspace`; consultation rows do not receive the product detail action. Selecting the Finance preset in a blank ordinary session enters a listed consultation Workspace; selecting another preset in a blank Finance session returns to the prior regular Workspace. Selecting a client first enters its Workspace, then stages the client in the new session. Archiving the selected Finance Session preserves the Finance category and reactivates that Session's startable Workspace, preventing the empty selection from falling back to regular workspaces. Removing the Finance product plugin leaves no Finance condition in the generic Workspace browser. The Windows native directory picker binds the active foreground window as its modal owner, so either section's add action raises the chooser immediately instead of leaving it behind the application.

The Finance preset adds one `finance-client-context` row that imports the Host package's separate context entry. The context listener filters by the live composed preset and falls back to the durable session preset for restored sessions. This handles blank live agents whose session header has not yet recorded the preset while keeping Standard and other presets unaffected. Both new packages and their composition rows are declared in `product.json.financeExtension`; removing those rows removes the capability without changing Agent Loop or official product behavior.

The saved Youcheng configuration binds one explicit ledger ID. Connection verification runs after saving and remains independent from catalog commits, so an unavailable vendor cannot turn a completed save into an ambiguous failure. The Host checks credentials and exact ledger membership, and the product Client supplies the account name and semantic badge through the generic Workspace category. A successful authentication alone is insufficient because one keypair may expose multiple ledgers. Environment labels resolve through deployment-owned origins and may share the same address; credentials and verified ledger selection, not the label, determine API access. Check state is volatile and version-bound, preventing stale asynchronous success after a customer edit or Host restart. No accounting write or multi-ledger selection is introduced.

The details editor owns a bounded dialog with an independently scrolling field region and a non-scrolling heading and action row. This keeps Save and Cancel reachable on short viewports without changing the shared Modal or its other consumers. Finance-policy notes stay available as collapsed optional context instead of occupying a permanent textarea or deleting existing customer data. Browser verification checks control visibility and field overflow at desktop, short-window, narrow, and landscape sizes.

Ledger discovery is separate from binding verification: the loopback-only Remote accepts unsaved application credentials, authenticates without a ledger filter, and returns names and IDs for explicit selection. It does not persist credentials or change the saved connection's badge or token cache. The Client derives the binding ID from the ledger selector without a separate ID input, invalidates choices when authentication fields change, and ignores superseded lookup responses. A returned ledger is a candidate authorized by the application, not evidence that it belongs to the current customer. Adapter, Host, Client, and assembled Web coverage pin credential isolation, cancellation, revision conflicts, empty/failing discovery, name-based selection, and save-time revalidation.

Configured active Youcheng rows also expose a loopback-only inline link action through `WorkspaceCategoryRegistry.activateWorkspaceBadge`. It reuses saved-configuration verification after Host restart without reopening or saving the editor, changing row expansion, or staging a session. The Client suppresses duplicate in-flight requests and retains same-version check progress and results across overlapping catalog refreshes; a changed record version or Host connection reset invalidates the attempt. Failure leaves the action retryable; successful verification alone restores the account name and green dot. Automatic startup checks are not enabled.

Connection failure categories distinguish deadline expiry, including body reads, from network faults. HTTP 403 alone establishes access denial, not its underlying policy; an explicit vendor IP rejection retains the allowlist category. No raw vendor error is exposed. Focused tests pin these distinctions; the restarted Web scenario also verifies loss of green status on access denial and recovery without catalog changes.

The same session-bound Finance service owns read-only reference queries. One small preset consumer covers the five documented reference kinds without a new workflow engine. The Host validates current identity and credentials, preserves hierarchy and endpoint-specific states, and projects only allowed fields. No cursor or total is documented, so bounded results explicitly retain unverified coverage and exact filters never claim global absence or uniqueness. A green connection is not used as permission to bypass query-time validation. Reference rows enter ordinary tool-result events, not a new persistence format.

## Alternatives considered

- **Build a CRM.** Rejected because contacts, contracts, sales, billing, and relationship workflows are outside the Finance context requirement.
- **Read the latest client record on every model request.** Rejected because editing a record would rewrite the effective facts of historical conversations.
- **Write every selector change to the session log.** Rejected because pre-turn experimentation is not model-visible; only the selection used by the first request belongs in durable history.
- **Allow a general session to bind later.** Rejected because earlier answers were produced without that entity and a mid-session switch creates ambiguous accounting context.
- **Send full records through the ordinary session projection.** Rejected because tax identifiers, mappings, policy notes, and external-system references are not needed by the conversation header.
- **Store the Youcheng AppSecret in the client catalog.** Rejected because full client reads, Workspace profile files, and immutable session snapshots must not carry an external-system secret.
- **Maintain account mappings in the client-details form.** Rejected because Youcheng account subjects are authoritative API data; any future cross-system mapping belongs to the operation that needs it, not the connection record.
- **Put the selector directly in `ui-conversation`.** Rejected because official UI may own only the generic slot and fallback, while Finance copy, state, and behavior remain in a removable product plugin.
- **Mix customer directories into ordinary Workspaces.** Rejected because ordinary search, session creation, and directory management would expose customer roots and allow a Finance session to start in the wrong Workspace.
- **Treat a per-session work directory as the customer record directory.** Rejected because records and policies must be shared across the customer's sessions while drafts and temporary files remain session-isolated.
- **Move uploads or work files between stages.** Rejected because cancellation, retry, audit, and manual recovery require the source to remain available after import, publication, or archival.
- **Require one literal “publish result” command.** Rejected because the Agent can map ordinary final-version, export, delivery, and formal-save requests to one narrowly validated tool; unclear intent still remains a draft.

## Verification

Connection tests cover exact ledger matching, safe failures, token reuse, deadlines, cancellation, and invalidation during concurrent edits. The real Web composition exercises save, green/red badges, preserved secrets, and the editor snapshot with only the vendor network substituted. The loopback restriction is tested on generated slash endpoints before shared-channel interception, so a trusted remote hostname cannot invoke saved credentials through a different route spelling.

Store tests cover client and Workspace-presentation persistence, create, update, archive, duplicate credit codes, stale revisions, atomic writes, and corrupt-file preservation. Domain tests also cover Youcheng configuration validation, credential separation and preservation, stale-revision rejection before credential mutation, and exclusion of connection settings from the model prompt. Client tests cover the two form sections, conditional Youcheng fields, unsupported-system placeholders, the absence of account mappings, the customer-only details action and menu order, create/edit/archive flows, consultation/client selection, preset routing, owner-scoped composer blocks, unified upload claiming, ordinary-session fallback, and image rollback.

The shipped Web composition keylessly assembles both a general Finance prompt and a client-bound Finance prompt through the real preset mount. The snapshots prove that Standard keeps no Finance context, general Finance explicitly has no customer, a bound Finance request receives only its logged immutable snapshot while periods remain task-specific, and only Finance receives the controlled file tool and lifecycle instructions. Product-layer, user-data, persistence-catalog, and Cordis-config gates require the package inventory, preset rows, private Remote methods, known file events, protected `harness/finance` fixture, and removable composition.

The restarted Host browser scenario reuses saved credentials and captures the inline action's unverified, checking, failed, and connected states. It exercises keyboard retry and asserts unchanged catalog bytes and row expansion.

## Consequences

Finance is a complete removable business module: the catalog owns business facts and non-secret connection settings, the credential provider owns AppSecret values, dedicated Finance Workspaces isolate files and sessions, the controlled file lifecycle records imports and committed copies, and the product Client plugin owns selection, routing, configuration, and the upload handoff. Record changes are safe for future work and cannot alter prior model context. Future deterministic calculators, Youcheng workflows, SDOO connectors, and compliance services can accept an Agent and call `requireBoundClient()` instead of implementing customer selection or directory boundaries. The split prevents natural-language tools and model prompts from receiving credentials, at the cost of coordinating catalog and credential commits under one catalog lock. An upstream Harness upgrade should adjust only `src/compat.ts`, the generic slot owner, Workspace-category integration, upload event integration, or the generated Remote integration when those APIs change; storage, credentials, file lifecycle, workspaces, immutable binding, and product UI remain separate.
