# Agent Note: Xiaojing Finance client domain and immutable session context

Status: implemented

English | [中文](2026-08-27-xiaojing-finance-client-domain.zh.md)

## Problem

Finance mode could research official tax sources but had no durable way to distinguish a general consultation from work for one taxpayer entity. Putting mutable customer fields directly into browser state or rebuilding context from the latest customer record would allow two sessions to mix entities and would change the facts seen by an old conversation after the record was edited. A CRM would add unrelated contacts, sales, contracts, and billing scope without solving model-context integrity.

The implementation also needed to preserve the repository rule that model-visible input is reconstructable from the session log, keep product behavior outside official Harness UI owners, and make future Youcheng and SDOO services reject unbound sessions through one shared guard.

## Decision

`@deepseek-ai/dsh-xiaojing-finance-domain` is the Xiaojing-only Host capability. It stores one record per taxpayer entity in `$DSH_HOME/finance/clients-v1.json`. The document has schema version `1`, a whole-file revision, and record-local versions. Mutations use compare-and-swap revision checks, a process-safe file lock, and atomic replacement. Corrupt data rejects plugin initialization and remains unchanged. Records may be archived but not deleted, so historical session references stay valid.

A blank Finance session starts in general-consultation state. Client selection is staged only in Host memory before the first turn. The first model request resolves the staged record, appends and flushes one `finance/client-bound` event, then contributes its text to the request. That event contains only the immutable record snapshot and record version. A month, quarter, or year belongs to the specific Finance Skill request and is read from the user instruction or requested when absent; it is not fixed on the client or session. General requests log no binding and receive an explicit no-client context that prohibits inferred customer facts. `requireBoundClient()` is the single precondition for future client-specific finance services.

Request preparation can flush the binding before `turn/start`; interruption in that interval leaves a session both blank and durably bound. Re-entering that customer's Workspace is idempotent: the Host verifies the same client and `cwd`, returns the locked safe view, and still rejects general mode or another client. The Client renders the customer name from that safe view, keeps both selectors locked, and leaves the composer available.

The `financeClient` session projection folds the durable event but exposes only client display name and state to browser clients. Full tax identifiers, policy notes, mappings, and external-system identifiers remain Host data. The generated `financeClients` Remote exposes summaries and safe session state generally; full reads, mutations, and staging are loopback-only.

`@deepseek-ai/dsh-client-ui-xiaojing-finance-clients` registers Customer Management after Agent Presets and before Channels. It fills the new product-neutral `conversation.hero.context` slot only for blank Finance sessions and registers a read-only context label in active session headers. The `Consultation / Client` selector adds an owner-scoped composer block only while client mode has no selected client. `ComposerBlockRegistry.setOwned()` allows Finance to remove only its own block without clearing independent model, upload, Goal, or Plan constraints.

Finance also owns a file and conversation category separate from ordinary user workspaces. Product configuration fixes its root beneath `小兢会计工作区/Finance工作区`, with one Workspace displayed as `Consultation` for unbound sessions and one `clients/<stable-client-id>` Workspace per taxpayer entity. The client root is the immutable `cwd` for all of that client's sessions and owns profile, policy, source, session-isolated work, deliverable, and archive directories; task Skills create period-specific children when needed. The Host validates the actual `cwd` before staging and model use, structurally rejecting cross-client binding. Client creation provisions directories and registers the Workspace before committing the catalog; failures roll back new resources. Startup recovery removes a registration left by an interrupted create while preserving its files for recovery.

The same Host capability owns a controlled, copy-only lifecycle for those directories. A Client extension event lets the existing upload button hand a completed local upload to Finance only when the session is client-bound; the Host copies it into `02-原始资料`, while consultations and other presets keep the ordinary upload route. Every session owns one `03-会话作业/<session-id>` directory with an atomically written `会话信息.json` identity manifest; complete conversation history remains in the Harness session store, and the customer directory contains only work files plus that manifest. The Finance-only `finance_files` tool copies a session-work file into `04-成果输出` when the user's natural-language request identifies a final, exported, delivered, or formally saved result, and copies an explicitly archived managed file into a date child of `05-归档`. Draft or ambiguous work stays in `03`, and neither operation removes its source.

`.xiaojing-finance-files-v1.json` is an append-only, revisioned index in each client root. It records the owning client and session, operation, absolute committed path, size, SHA-256 digest, and source-record relationship. A successful copy appends and flushes a matching `finance/file-imported`, `finance/file-published`, or `finance/file-archived` session event, making every model-visible managed path reconstructable from the log. Path validation resolves regular non-symlink files against the upload root, current session work directory, or selected client directories. Atomic destination creation and index replacement prevent overwrite and partial metadata; a corrupt index stops the operation without replacing the damaged file. These controls govern the unified upload and Finance tool paths, not arbitrary Full Access shell writes.

`$DSH_HOME/finance/workspace-presentation-v1.json` owns editable Workspace titles and Finance-list membership independently of customer records and Workspace registrations. It uses schema version `1`, a revision, process-safe locking, and atomic replacement. Removing a Workspace is a non-destructive list operation: its registration, directory, customer record, and sessions remain intact, hidden Finance registrations stay reserved from ordinary Workspaces, and selecting the same directory restores the item. The domain rejects removing the final listed consultation Workspace.

Generic `ui-workspace` adds only the `WorkspaceCategoryRegistry` extension point and contains no Finance copy or recognition rule. The extension supports product categories, nested sections, product-neutral semantic section icons, reserved and visible membership, provider-owned rename and remove operations, and the active preset's Workspace-picker scope. It renders nested sections as contiguous groups in provider order even when the global Workspace registry interleaves their members, while preserving registry order within each section. The Finance Client plugin supplies `Regular workspaces / Finance workspaces` labels and membership: `Clients` uses the person icon and precedes `Consultation`, which uses the discussion icon; their child Workspaces retain folder icons and share the same row actions. Selecting the Finance preset in a blank ordinary session enters a listed consultation Workspace; selecting another preset in a blank Finance session returns to the prior regular Workspace. Selecting a client first enters its Workspace, then stages the client in the new session. Archiving the selected Finance Session preserves the Finance category and reactivates that Session's startable Workspace, preventing the empty selection from falling back to regular workspaces. Removing the Finance product plugin leaves no Finance condition in the generic Workspace browser. The Windows native directory picker binds the active foreground window as its modal owner, so either section's add action raises the chooser immediately instead of leaving it behind the application.

The Finance preset adds one `finance-client-context` row that imports the Host package's separate context entry. The context listener filters by the live composed preset and falls back to the durable session preset for restored sessions. This handles blank live agents whose session header has not yet recorded the preset while keeping Standard and other presets unaffected. Both new packages and their composition rows are declared in `product.json.financeExtension`; removing those rows removes the capability without changing Agent Loop or official product behavior.

## Alternatives considered

- **Build a CRM.** Rejected because contacts, contracts, sales, billing, and relationship workflows are outside the Finance context requirement.
- **Read the latest client record on every model request.** Rejected because editing a record would rewrite the effective facts of historical conversations.
- **Write every selector change to the session log.** Rejected because pre-turn experimentation is not model-visible; only the selection used by the first request belongs in durable history.
- **Allow a general session to bind later.** Rejected because earlier answers were produced without that entity and a mid-session switch creates ambiguous accounting context.
- **Send full records through the ordinary session projection.** Rejected because tax identifiers, mappings, policy notes, and external-system references are not needed by the conversation header.
- **Put the selector directly in `ui-conversation`.** Rejected because official UI may own only the generic slot and fallback, while Finance copy, state, and behavior remain in a removable product plugin.
- **Mix customer directories into ordinary Workspaces.** Rejected because ordinary search, session creation, and directory management would expose customer roots and allow a Finance session to start in the wrong Workspace.
- **Treat a per-session work directory as the customer record directory.** Rejected because records and policies must be shared across the customer's sessions while drafts and temporary files remain session-isolated.
- **Move uploads or work files between stages.** Rejected because cancellation, retry, audit, and manual recovery require the source to remain available after import, publication, or archival.
- **Require one literal “publish result” command.** Rejected because the Agent can map ordinary final-version, export, delivery, and formal-save requests to one narrowly validated tool; unclear intent still remains a draft.

## Verification

Store tests cover client and Workspace-presentation persistence, create, update, archive, duplicate credit codes, stale revisions, atomic writes, and corrupt-file preservation. Domain tests cover default general context, consultation and client Workspace provisioning, durable rename, non-destructive list removal and restoration, the final-consultation invariant, create rollback, interrupted-registration recovery, cross-client `cwd` rejection, staging, idempotent reopening of a blank session bound to the same client, reassignment rejection, first-turn locking, immutable snapshots, historical reconstruction, two-client isolation, safe projections, archived clients, Standard-session rejection, upload import, publication, archival, source preservation, cross-client path rejection, and corrupt-index preservation. Client tests cover product-profile and loopback registration, Settings ordering, create/edit/archive flows, compact consultation/client selection, the locked safe view for a blank bound session, general default, first-turn labels, connection reset, regular/Finance Workspace isolation, both Finance sections' row actions, selected-session archive routing, preset routing, owner-scoped composer blocks, unified upload claiming, ordinary-session fallback, and image rollback.

The shipped Web composition keylessly assembles both a general Finance prompt and a client-bound Finance prompt through the real preset mount. The snapshots prove that Standard keeps no Finance context, general Finance explicitly has no customer, a bound Finance request receives only its logged immutable snapshot while periods remain task-specific, and only Finance receives the controlled file tool and lifecycle instructions. Product-layer, user-data, persistence-catalog, and Cordis-config gates require the package inventory, preset rows, private Remote methods, known file events, protected `harness/finance` fixture, and removable composition.

## Consequences

Finance is now a complete removable business module: the catalog owns business facts, dedicated Finance Workspaces isolate files and sessions, the controlled file lifecycle records imports and committed copies, the product Client plugin owns selection, routing, and the upload handoff, and generic Harness owns only slots, category extension points, and the optional upload event. Record changes are safe for future work and cannot alter prior model context. Future deterministic calculators, Youcheng workflows, SDOO connectors, and compliance services can accept an Agent and call `requireBoundClient()` instead of implementing customer selection or directory boundaries. An upstream Harness upgrade should adjust only `src/compat.ts`, the generic slot owner, Workspace-category integration, upload event integration, or the generated Remote integration when those APIs change; storage, file lifecycle, workspaces, immutable binding, and product UI remain separate.
