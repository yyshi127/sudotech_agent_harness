# Agent Note: Xiaojing semantic browser and Windows automation

Status: implemented

English | [中文](2026-08-21-xiaojing-semantic-automation.zh.md)

## Problem

Xiaojing needs browser and native Windows application control immediately after installation. Requiring users to discover external plugins, install drivers, configure another API key, or teach each new conversation how to operate the computer does not satisfy that product behavior. Pixel and OCR automation would also add a large runtime, weaker target identity, and a second visual capability that is explicitly outside this change.

## Decision

Two independent Cordis packages own the capabilities: `@deepseek-ai/dsh-xiaojing-browser-control` registers `browser_control`, and `@deepseek-ai/dsh-xiaojing-computer-control` registers `computer_control`. They are separate rows in the Web composition, so a development overlay can remove either capability without editing Harness core. The product composition enables both. A third removable Client plugin, `@deepseek-ai/dsh-client-ui-xiaojing-browser-control`, contributes the standalone loopback-only “Browser Control” settings section without modifying General settings or an official UI package. Their tools are deliberate deployment-global rows because every Xiaojing session, including a user-authored preset that suppresses runtime context, must receive the installed schemas and their routing descriptions. The Xiaojing Host product plugin adds a combined dynamic context for sessions that accept it. The schemas and optional combined context both direct the model toward the shortest deterministic route: direct file, data, editing, and command tools remain primary, websites use browser control, and Windows control supplements them only when a task requires a native application's visible interface.

Browser control uses `playwright-core` to start installed Edge or Chrome visibly with a dedicated persistent profile for each browser below `DSH_HOME`. The durable `xiaojing-browser-control` setting defaults to Edge and supplies the browser when a task does not name one. An explicit Chrome or Edge request overrides that task without changing the durable default, and both controlled contexts can remain available without cross-browser fallback. Before launching Chrome on Windows, the provider queries both mandatory policy hives for `UserDataDir`; if policy would redirect the isolated profile into the live personal profile, startup fails before spawning Chrome. `open` discovers user-opened and tool-opened pages in the requested controlled context, then prefers an exact destination, a same-origin page, or a blank page, removes redundant blank pages in that context, and creates another tab only when none is suitable. Later semantic actions continue on the session's active page. Users can sign in and minimize the window while protocol-level DOM actions continue without physical mouse or keyboard input. The tool returns bounded visible text and semantic interactive targets. A target is an opaque, session-owned identifier retaining the exact observed DOM node; it expires after an action or tab switch, and a detached or replaced node fails instead of allowing a positional locator to hit another control. Model requests to this tool cannot contain CSS selectors, JavaScript, CDP commands, browser profile paths, or password values. Product prompts prefer browser control for websites, require startup failures to be reported without an unsolicited cross-browser retry, but do not intercept separate shell, PowerShell, or CDP operations. Route checks classify frame-owned and Service Worker requests separately; a private Service Worker destination is allowed only while an approved same-origin page remains open. The Windows product does not bundle Chrome for Testing. A configured executable remains available only for tests or a controlled deployment.

Windows control maintains one persistent Windows PowerShell 5.1 helper through the Harness subprocess capability. The helper accepts a bounded newline-delimited JSON protocol, queries the Windows Start application catalog, launches one selected catalog entry, and exposes visible top-level windows plus `System.Windows.Automation` controls. The model sees only expiring session-owned application IDs; it cannot supply or read application registration IDs, executable paths, PowerShell source, or arbitrary shell commands. A successful launch consumes the application listing and returns a fresh window list. Window and control identifiers are likewise opaque, session-owned, bounded, and invalidated after state changes. Every helper process includes a unique instance component in all of its opaque IDs, preventing an ID retained across a helper restart from resolving to an unrelated new object.

Browser operations serialize per agent session; the single Windows helper serializes all Windows operations. Closing browser control cancels running and queued operations and waits for them to settle before a later request may relaunch the selected browser. An unexpected browser exit invalidates queued work from that instance, while plugin disposal permanently rejects new work and waits for browser operations to become quiescent. Cancelling the browser's last page creates a replacement blank page before closing the failed page, which keeps the visible process available for recovery. Both providers propagate cancellation, invalidate cross-session opaque IDs, recover after an interrupted owned process, and release their browser or helper process when the plugin unloads. Private or loopback browser navigation, local file upload, committing keys, high-impact application launches, submissions, payments, deletions, sends, and comparable native actions require one-use approval. A missing, cancelled, unavailable, or rejected approval fails closed. Password fields, native browser or operating-system dialogs, UAC, secure desktop, elevated applications, pixel-only controls, CAPTCHAs, and canvas-only websites remain unsupported.

## Alternatives considered

- **Bundle Chrome for Testing.** The measured unpacked runtime is 415.4 MiB, and the [official Chrome for Testing documentation](https://developer.chrome.com/docs/automation-and-testing/chrome-for-testing) limits it to automation that consumes trustworthy content. Shipping it would add another browser update and security responsibility. The product instead uses a selected system-managed Edge or Chrome installation and defaults to Edge.
- **Let the model supply selectors, JavaScript, CDP, coordinates, or PowerShell.** These inputs are brittle and create arbitrary execution channels. Bounded semantic observations and fixed actions keep the execution surface reviewable.
- **Let the model launch an executable path or command.** That would duplicate existing command capabilities and turn a convenience operation into an arbitrary process launcher. The provider resolves opaque IDs only from the current Windows Start application catalog.
- **Use OCR or screenshots as the primary control path.** This adds a large inference runtime and coordinate drift while weakening control identity. Local OCR and vision remain a separate future capability.
- **Depend on an external RPA service or browser extension.** That approach adds installation, authentication, update, and availability dependencies and is not an open-box desktop capability.
- **Block shell, PowerShell, or CDP browser automation at the Host.** A hard block would remove existing general-purpose capabilities and could reject legitimate diagnostics. The product supplies routing guidance and a stable browser tool without turning that preference into an execution interceptor.
- **Add the tools to every preset file.** User-created presets would still miss them, and future preset changes could silently remove a product capability. Deployment-global registration plus a dynamic capability prompt gives every session the same installed set.

## Verification

Browser package tests cover private-address classification, protocol rejection, Windows Chrome `UserDataDir` policy detection, a real browser page, Service Worker traffic without an associated frame, discovery and reuse of an existing tab, redundant blank-tab cleanup, same-origin navigation without tab growth, explicit task browser overrides alongside the saved default, simultaneous Edge and Chrome contexts, semantic observation, exact-node rejection after DOM replacement, fill, protected submit classification, cross-session and stale-observation rejection, bounded tab listing, interrupted-navigation recovery, queued-operation cancellation during close, unexpected context exit, browser relaunch, and quiescent plugin disposal. Client tests pin the standalone section identity, Xiaojing and loopback guards, Edge default, Chrome write, and teardown removal. A child-process regression also runs the browser package through the declared `tsx` ESM source launcher, so Playwright page callbacks are verified after the development-time transformation. Computer package tests validate helper responses, application catalog ownership, bounded window listing, and high-impact launch classification, and use a real WinForms window to cover cross-session rejection, observation, value editing, protected-action classification, invocation, bounded waiting, interruption recovery, rejection of pre-restart opaque IDs, and helper relaunch. Windows live verification resolves and launches Notepad through its opaque application ID and confirms the resulting UI Automation window. The keyless assembled snapshot pins both schemas and routing descriptions even for a preset that suppresses runtime context; the shipped-composition test pins the combined context for ordinary sessions. Product-layer, Cordis configuration, workspace, type, build, documentation, and desktop data-path gates cover the assembled application.

## Consequences

Xiaojing can operate ordinary semantic websites in the saved default browser, honor an explicitly requested browser for one task, and control native Windows applications without another API key, browser driver installation, or OCR runtime. It can also open ordinary Start-registered applications without exposing a general process-launch interface. Direct tools remain faster and more reliable for work that does not require a visible application. Edge and Chrome login states persist independently across ordinary application restarts and in-place upgrades, and their controlled contexts can coexist, while opaque observations remain ephemeral. A mandatory Windows Chrome `UserDataDir` policy prevents the isolated Chrome context and is reported without touching the live profile; users on such a machine must select Edge or change that managed policy. Minimized DOM automation avoids input contention for ordinary page controls, but native dialogs can still require user-visible intervention or Windows control. Routing remains guidance rather than enforcement, so a model can still choose a less suitable general-purpose execution path. The result is not universal computer vision: sites or applications that expose no useful DOM or UI Automation semantics require a later, independently removable vision capability.
