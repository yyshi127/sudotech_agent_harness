# Agent Note: Xiaojing semantic browser and Windows automation

Status: implemented

English | [中文](2026-08-21-xiaojing-semantic-automation.zh.md)

## Problem

Xiaojing needs browser and native Windows application control immediately after installation. Requiring users to discover external plugins, install drivers, configure another API key, or teach each new conversation how to operate the computer does not satisfy that product behavior. Pixel and OCR automation would also add a large runtime, weaker target identity, and a second visual capability that is explicitly outside this change.

## Decision

Two independent Cordis packages own the capabilities: `@deepseek-ai/dsh-xiaojing-browser-control` registers `browser_control`, and `@deepseek-ai/dsh-xiaojing-computer-control` registers `computer_control`. They are separate rows in the Web composition, so a development overlay can remove either capability without editing Harness core. The product composition enables both. Their tools are deliberate deployment-global rows because every Xiaojing session, including a user-authored preset that suppresses runtime context, must receive the installed schemas and their routing descriptions. The Xiaojing Host product plugin adds a combined dynamic context for sessions that accept it. The schemas and optional combined context both direct the model toward the shortest deterministic route: direct file, data, editing, and command tools remain primary, websites use browser control, and Windows control supplements them only when a task requires a native application's visible interface.

Browser control uses `playwright-core` to start the installed Microsoft Edge with a dedicated persistent profile below `DSH_HOME`. It returns bounded visible text and semantic interactive targets. A target is an opaque, session-owned identifier that expires and becomes invalid after an action or tab switch. Model requests cannot contain CSS selectors, JavaScript, CDP commands, browser profile paths, or password values. Route checks classify frame-owned and Service Worker requests separately; a private Service Worker destination is allowed only while an approved same-origin page remains open. The Windows product does not bundle Chrome for Testing. A configured Chromium executable remains available only for tests or a controlled deployment.

Windows control maintains one persistent Windows PowerShell 5.1 helper through the Harness subprocess capability. The helper accepts a bounded newline-delimited JSON protocol, queries the Windows Start application catalog, launches one selected catalog entry, and exposes visible top-level windows plus `System.Windows.Automation` controls. The model sees only expiring session-owned application IDs; it cannot supply or read application registration IDs, executable paths, PowerShell source, or arbitrary shell commands. A successful launch consumes the application listing and returns a fresh window list. Window and control identifiers are likewise opaque, session-owned, bounded, and invalidated after state changes.

Browser operations serialize per agent session; the single Windows helper serializes all Windows operations. Both providers propagate cancellation, invalidate cross-session opaque IDs, recover after an interrupted owned process, and release their browser or helper process when the plugin unloads. Cancelling the browser's last page creates a replacement blank page before closing the failed page, which keeps the visible Edge process available for recovery. Private or loopback browser navigation, local file upload, committing keys, high-impact application launches, submissions, payments, deletions, sends, and comparable native actions require one-use approval. A missing, cancelled, unavailable, or rejected approval fails closed. Password fields, UAC, secure desktop, elevated applications, pixel-only controls, CAPTCHAs, and canvas-only websites remain unsupported.

## Alternatives considered

- **Bundle Chrome for Testing.** The measured unpacked runtime is 415.4 MiB, and the [official Chrome for Testing documentation](https://developer.chrome.com/docs/automation-and-testing/chrome-for-testing) limits it to automation that consumes trustworthy content. Shipping it would add a second browser update and security responsibility. The product instead uses the Windows-supported, auto-updating Edge installation.
- **Let the model supply selectors, JavaScript, CDP, coordinates, or PowerShell.** These inputs are brittle and create arbitrary execution channels. Bounded semantic observations and fixed actions keep the execution surface reviewable.
- **Let the model launch an executable path or command.** That would duplicate existing command capabilities and turn a convenience operation into an arbitrary process launcher. The provider resolves opaque IDs only from the current Windows Start application catalog.
- **Use OCR or screenshots as the primary control path.** This adds a large inference runtime and coordinate drift while weakening control identity. Local OCR and vision remain a separate future capability.
- **Depend on an external RPA service or browser extension.** That approach adds installation, authentication, update, and availability dependencies and is not an open-box desktop capability.
- **Add the tools to every preset file.** User-created presets would still miss them, and future preset changes could silently remove a product capability. Deployment-global registration plus a dynamic capability prompt gives every session the same installed set.

## Verification

Browser package tests cover private-address classification, protocol rejection, a real Microsoft Edge page on Windows, Service Worker traffic without an associated frame, semantic observation, fill, protected submit classification, cross-session and stale-observation rejection, bounded tab listing, first-page and later interrupted-navigation recovery, and browser relaunch. A child-process regression also runs the browser package through the declared `tsx` ESM source launcher, so Playwright page callbacks are verified after the development-time transformation. Computer package tests validate helper responses, application catalog ownership, bounded window listing, and high-impact launch classification, and use a real WinForms window to cover cross-session rejection, observation, value editing, protected-action classification, invocation, bounded waiting, interruption recovery, and helper relaunch. Windows live verification resolves and launches Notepad through its opaque application ID and confirms the resulting UI Automation window. The keyless assembled snapshot pins both schemas and routing descriptions even for a preset that suppresses runtime context; the shipped-composition test pins the combined context for ordinary sessions. Product-layer, Cordis configuration, workspace, type, build, documentation, and desktop data-path gates cover the assembled application.

## Consequences

Xiaojing can operate ordinary semantic websites and native Windows applications without another API key, browser driver installation, or OCR runtime. It can also open ordinary Start-registered applications without exposing a general process-launch interface. Direct tools remain faster and more reliable for work that does not require a visible application. Browser state persists across ordinary application restarts and in-place upgrades inside the dedicated profile, while opaque observations remain ephemeral. The result is not universal computer vision: sites or applications that expose no useful DOM or UI Automation semantics require a later, independently removable vision capability.
