# Agent Note: 财务维护确认身份

Status: implemented

[English](2026-09-14-finance-maintenance-confirmation-identity.md) | 中文

## Problem

财务维护会先持久保存准确的准备操作，再请求财务专属强制确认。此前确认展示有成目标及版本，却没有展示本地准备操作 ID，导致测试人员或审计记录无法将可见确认与随后占用并发送的持久操作明确对应。

## Decision

凭证删除及日记账删除的财务专属强制确认同时展示本地准备操作 ID、准确版本及目标预览。预留仍在确认前后重新核验完整已保存预览及当前配置，发送仍受持久目标占用约束且只能执行一次。缺少确认或确认被拒绝时，在发送有成变更请求前停止，并保留操作供只读检查。

产品级破坏性操作确认仍是独立的第一层。本次变更不绕过任一确认层，不接受调用方提供的批准，不增加测试模式豁免，也不扩大已授权目标范围。

## Alternatives considered

**仅展示有成目标 ID 和版本。** 不采用，因为明确未发送后，同一外部目标可能具有多个分别准备的本地尝试，而较早的已消耗或结果未知尝试必须能够区分。

**本地 ID 缺失时放宽真实验收脚本。** 不采用，因为这会认可无法对应持久操作的确认，并掩盖产品审计缺口。

## Verification

Host 测试断言两类强制确认原因都包含生成的准备操作 ID、金额及目标。完整 Finance Host 测试通过 137 项。正式凭证删除及日记账删除 Web 场景通过快照刷新及独立回放。真实主应用验收在调用两类有成删除接口前拒绝旧确认；新的合成日记账验证修正后的确认。

实验脚本只在原详细确认被拒绝、会话空闲、原持久操作仍为 prepared 且没有预留或结果时，允许在一个新运行中复用已经核验附件的凭证样例。来源只绑定一个子运行，仅复制不可变样例证据，不复制操作意图。八项离线保护测试覆盖错误账套、版本变化、已接收或未知操作及拒绝证据缺失。新运行必须准备另一个操作并取得两层确认，不重发原操作。无关记录使用删除前的最新基线比较，避免把等待附件过期期间其他已授权测试的变更误归因于凭证删除。

## Consequences

确认文本增加一个不透明的本地标识，但获批操作现在可以在对话框、持久记录和恢复证据之间明确对应。确认被拒绝或发送意图已消耗的尝试不会被静默复用；仅在既有安全规则允许再次尝试时创建新的操作。
