# Agent Note: Finance business creation

Status: proposed

English | [中文](2026-09-09-finance-business-creation.zh.md)

## Problem

Voucher creation does not cover journals, receivables, payables or master-data creation. These operations have different identifiers, direction rules and readback evidence; reusing a voucher success response as their completion proof would conceal missing or incorrect business records.

## Proposal

Implement the five approved F3A capabilities in the Xiaojing finance domain, with separate business validation and reference resolution. Reuse approval, atomic persistence and bounded single-send primitives where applicable, without a general workflow engine. Each operation requires an editable local preview, mandatory confirmation of its exact version, durable reservation before sending and independent readback. Unknown outcomes retain the original reservation and cannot trigger an automatic resend. Master-data creation is a separately confirmed action, not an implicit response to a missing reference.

Journal requests use the returned cash-account ID in the vendor's subjectId field, not the accounting-subject ID. Exactly one money side is populated; the other is null. A selected category is checked for direction and same-name ambiguity because the write endpoint accepts categoryName rather than the reference ID. The predecessor requires separate Host qualification; zero is not an unexamined default. The initial pure preparation module grants no external write authority.

Readback compares selected category IDs: the vendor can prefix display names with income/expense markers. A successful ID response is retained before any comparison; a display-name discrepancy cannot trigger resending. Bounded accepted-ID lookup checks the exact record and its returned linkage/audit fields without claiming exhaustive history or actual payments. The two live journal fixtures qualify the internal API path. Separate assembled-app tests exercise the real approval UI, strict local version, rejection, single sending and unknown-result retention; mocked vendor results do not substitute for live business evidence.

Auxiliary-item preparation requires explicit category/code/name/maker/status, the independently selected ledger and an unfiltered returned category/item set. A duplicate code or name prevents creation; missing categories do not trigger implicit category creation. This pure validation does not qualify the live write endpoint or prove exhaustive absence. Status absent from vendor readback remains unknown even when the proposal explicitly requested enabled or disabled.

Subject preparation retains semantic debit/credit choices instead of reusing raw query flags. Explicit code/parent/category choices follow the documented4-2-2-2 structure. Existing or unknown leaves require independent historical-impact checks before promotion; an enabled existing branch is recorded separately. Duplicate codes and sibling names reject, while names under other parents remain visible. Scalar preparation does not qualify specific subject types, auxiliary/currency configuration or the live write mapping.

Master-data records share only the qualified subject/auxiliary empty-ID transport states. Business validation and payloads remain separate. Local target claims outlive individual previews so a new UUID or session cannot bypass an unknown attempt; a separately confirmed attempt can reuse the target only after durable explicit rejection or proven non-send. A claim saved without its matching reservation conservatively requires reconciliation, trading automatic recovery for protection against duplicate creation. Claims do not establish cross-device idempotency. The sender does not retry mutations, including after transient read failures or cancellation following dispatch.

The Finance Host and tools use the existing mandatory-approval service for subject/auxiliary exact versions, then persist a target claim before dispatch. Fresh reads check parent accounting and category identity as well as duplicate names/codes. Roots and existing ordinary branches are exposed; leaf-promotion and quantity accounting fail before confirmation. Explicit auxiliary/currency selections use the [accounting-options decision](../../implemented/feature/2026-09-14-subject-accounting-options.md) without changing parent settings. Root types require an observed same-category name in current-ledger references rather than an invented type catalog. The independently verified ledger35616 root1099 establishes null proposal parent, no public parent parameter and explicit empty-string readback parent; missing readback parent remains unavailable. Readback preserves unknown transport even when independently matching content is found. Keyless assembled-application snapshots cover both root and child confirmation panels, rejection, revision, one send and read-only recovery; live-model and main-runtime acceptance remain separately tracked.

The model-facing preparation command keeps action/kind/input at the top level rather than nesting another proposal object. Strict JSON and business validation remain required; malformed JSON is not repaired into a possible write. Subject type uses the vendor name supplied by the user, and Finance maker confirmation cannot be substituted with reimbursement membership. These descriptions and the Finance prompt address observed model routing/serialization errors without adding a generic intent parser or hidden accounting defaults.

Journal approval comparisons retain returned cash-account currency IDs, account types and raw directions alongside identity and labels. An unchanged account ID does not prove its accounting attributes are unchanged. These optional observations are persisted without inventing missing values, so existing accepted or unknown records remain readable. Changes detected before reservation reject approval; changes detected after reservation but before dispatch produce a durable not-sent result. Neither path sends a request or silently reuses the confirmation.

Subject reference notices use the independently qualified 0 debit/1 credit readback mapping. Ledger35616 fixtures100297 and100298 return raw0 and raw1 respectively and were independently checked against the vendor UI;100298 retains its original failed debit-intent comparison. This evidence qualifies direction meanings, not that failed creation intent. Retaining the earlier unqualified notice would contradict subject preparation/readback and mislead subsequent model choices. Missing directions remain absent; query rows are not given inferred defaults. Focused reference tests and the assembled Finance reference transcript pin both the notice and retained missing-field behavior.

Reference projections retain the vendor subjectType name for model-visible type selection and inspection; Host validation alone does not give the model that evidence. Missing/null types stay omitted, empty strings stay empty, and untrusted non-string or oversized values reject. Both the tool schema description and returned notices state the qualified direction meanings. The assembled Finance reference scenario checks the actual model tool description and transcript, including a child with no type or direction, instead of testing only an isolated notice. This avoids hardcoded type catalogs or inherited defaults while preserving read-only operation and result bounds.

Open-item mapping resolves auxiliary category and item identities before constructing `categoryName:itemName`. The vendor clarification and independently accepted receivable72595 and payable72596 establish this format; the earlier bare-name rejections are not evidence of a server defect. Scalar validation and formatting remain separate from authorization, account discovery and durable sending. The public cash-account query does not return AR/AP accounts even with the observed type5/type6 values; successful laboratory requests using independently observed account IDs do not justify hardcoding those IDs or treating existing business rows as enabled-account configuration.

Open-item reservations reuse atomic files and locks, not voucher-specific identities or a general workflow engine. Approval occurs outside the lock; the exact version is checked again under lock before preserving the complete request as uncertain. This prevents repeat sends for that operation, not equivalent new proposals. Independent public readback compares the original accepted ID, business content, account/category IDs, maker, counterparty, empty associations and unaltered outstanding balance. Missing settlement fields stay unknown. Accepted transport, successful readback and full application acceptance remain separate evidence. The documented-optional accountId cannot be omitted in the qualified payable case: a single omission experiment returns201/未指账户 with no new record. Existing business rows expose accountStatus/accountWb but are not a complete account inventory.

The open-item sender consumes a durably reserved request, reconstructs its fixed public payload and rechecks the unique ledger before the final Host callback. A lost response cannot enter a read-retry path. Tests cover both directions and preserve accepted IDs when cancellation follows receipt, while rejecting stale reservations and altered payloads before authentication. Public document ez7dJ32a defines accountWb as foreign-currency account; the vendor frontend maps truthy accountStatus to disabled, independently consistent with current UI and retained0/false rows. These fields may support bounded current-account verification but do not establish a complete account inventory or first-record discovery. No such discovery fallback is mounted.

An explicit existing-record reference page provides an additional, bounded source of account attributes, not a substitute for complete account discovery. Preparation retains the query and source record, validates its ledger/direction and rejects missing, disabled, conflicting or unqualified-currency accounts. Fresh auxiliary/category reads verify the same selected identities; unknown auxiliary status remains disclosed. The internal adapter produces previews for both live qualified fixtures without sending or changing their records. A first-ever account remains unresolved, so this evidence cannot complete F3A or justify a fixed-ID fallback.

The Finance preset mounts observed-account reads, local open-item preparation and exact-version creation. The Host uses the existing mandatory approval service, owner-scoped records and lifecycle tracking rather than a second authorization mechanism. Approval displays source limitations and selected labels; source/account/category/configuration changes invalidate it. Outcomes are persisted before independent readback, including cancellation after a received ID. Both-direction Host tests cover denial, concurrent revision, lost responses and owner isolation; the assembled keyless scenario exercises actual tool calls, confirmation and result UI. Live Host/model acceptance remains distinct from the two successful direct-API fixtures and cannot be inferred from these simulated scenarios.

## Alternatives considered

**Copy voucher orchestration wholesale:** voucher-specific identities, originals and accounting-entry readback do not qualify journal or open-item results. Share only proven primitives when their obligations match.

**Expose arbitrary API payloads:** this would let model arguments choose destinations, audit fields and unverified associations. Keep bounded business inputs and Host-owned references.

**Treat an accepted response as completion:** independent business readback is needed to distinguish accepted-but-unverified records from matched records, especially when an endpoint does not return a usable ID.

## Acceptance criteria

Main-Host qualification uses separately labeled fixtures, not preview-only examples. An exact-preview allow-once handler exercises mandatory approval without claiming a human click. Independent API and Chrome observations stay separate when auxiliary status is missing. Standalone audits recover owner-scoped records and compare prior returned references and voucher hashes without resending.

Enabled and disabled auxiliary fixtures independently qualify enableStatus1 and0: main-Host items191573 and191613 match code/name readback and their respective Chrome states. The public item query includes both but omits status. Presence in its result cannot establish enabled state, and laboratory UI evidence cannot be injected as a permanent product status assertion. The disabled fixture has no business associations and must remain unused.

All five capabilities pass focused validation and recovery tests, real assembled-application confirmation snapshots, natural-language scenarios and independent live readback in approved test ledger35616. Income and expense, receivables and payables each require evidence. New test records have stable labels and retained receipts; all pre-existing records remain. Modified previews, changed configuration, rejected approvals and duplicate submissions cannot write. Response loss and restart preserve unknown or accepted outcomes without blind retries. No audit, posting, closing, deletion, write-off or actual payment is added.

## Risks

An account visible in the vendor UI is not necessarily returned by the public cash-account query. Receivable/payable preparation must qualify a current reference source and public write mapping independently; successful cash journals do not establish either. Laboratory UI evidence may support a bounded parameter experiment, but it must not become a hardcoded production account catalog or a private-API fallback.

Public examples do not prove every field's live semantics, supported period or exhaustive query coverage. Category names can be ambiguous; missing values and incomplete reads cannot prove absence. Qualified ledger fixtures do not establish cross-device supplier idempotency. Development status records unqualified cases and incomplete integration rather than advertising them as available capabilities.
